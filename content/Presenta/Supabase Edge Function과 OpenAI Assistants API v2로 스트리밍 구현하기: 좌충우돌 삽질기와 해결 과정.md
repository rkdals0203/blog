
## 실시간 AI 큐카드 생성의 꿈


프로젝트 목표는 사용자가 업로드한 PDF 프레젠테이션 파일을 기반으로, 발표 흐름에 맞는 큐카드를 **실시간 스트리밍**으로 생성하여 제공하는 것이었습니다. 사용자는 PDF를 업로드하고, AI가 생성하는 큐카드를 즉각적으로 확인하며 발표를 준비할 수 있도록 사용자 경험을 높이고자 했습니다.

초기 접근 방식은 간단했습니다. OpenAI Assistants API v2에서 공식적으로 스트리밍을 지원하므로, 해당 기능을 활용하여 Edge Function에서 OpenAI API를 호출하고, 그 결과를 클라이언트로 실시간 전송(SSE, Server-Sent Events)하는 것이었죠. 하지만 현실은 녹록지 않았습니다. 😭

## 문제 해결의 대장정

### 1. AI 어시스턴트와의 오해 - "스트리밍, 정말 안 되나?"

개발 초기, Assistants API의 스트리밍 구현에 어려움을 겪으면서 혼란스러운 상황에 직면했습니다. 당시 참고했던 정보나 (저를 포함한) AI 어시스턴트조차 **Chat Completions API만 스트리밍을 지원하고 Assistants API는 지원하지 않는다**는 잘못된 안내를 하기도 했습니다. 이 때문에 잠시 Chat Completions API를 사용하며 PDF를 이미지로 변환하여 보내는 등의 복잡한 대안을 고려하기도 했습니다.

  ![[image copy.png]]

* **잘못된 정보:** Assistants API v2는 분명 스트리밍을 지원했지만, 초기 정보 부족이나 오해로 인해 불가능하다고 착각했습니다.

* **대안 모색의 함정:** 잘못된 정보에 기반하여 불필요하게 복잡한 대안(PDF -> 이미지 변환 후 Chat Completions 사용)을 고민하며 시간을 소모했습니다.

* **재확인과 확신:** OpenAI 공식 문서를 다시 꼼꼼히 확인하고, Assistants API v2에서 `stream: true` 옵션을 통해 스트리밍이 가능하다는 것을 **명확히 인지**한 후에야 올바른 방향으로 개발을 진행할 수 있었습니다.
  

### 2. 텅 빈 응답과의 싸움 

Assistants API 스트리밍이 가능하다는 확신을 가지고 코드를 구현했지만, 가장 먼저 마주한 문제는 Edge Function을 호출해도 클라이언트에서 **아무런 데이터도 받지 못하는 현상**이었습니다. 분명 Supabase Function Log에는 OpenAI API 호출이 성공했고, Vector Store에 파일 추가, Thread 생성, Message 추가, Run 생성 등 모든 과정이 정상적으로 기록되었으며, 심지어 스트림이 시작되고 (데이터 없이) 정상적으로 종료되었다는 로그까지 찍히고 있었죠. 클라이언트에서는 SSE 연결은 성공했지만, 어떠한 `data` 이벤트도 수신되지 않았습니다.

![[content/Presenta/image.png]]
지금은 잘 나오는 data response

**의심했던 원인들:**

1. **Assistant 자체의 문제:** Assistant가 PDF 파일을 제대로 참조하지 못하거나, 주어진 프롬프트로는 결과를 생성하지 못하는 경우.

2. **Vector Store 문제:** 파일이 Vector Store에 추가되었지만, 인덱싱이 완료되지 않아 Assistant가 접근하지 못하는 경우. 또는 Assistant와 Vector Store 간의 연결 설정 오류.

3. **Edge Function 내 스트림 처리 로직 오류:** OpenAI로부터 스트림 응답은 시작/종료 신호만 받고, 실제 데이터(delta)를 처리하거나 클라이언트로 전달하는 로직에 문제가 있는 경우.

  

**시도했던 해결 노력:**

* **OpenAI Playground 테스트:** 동일한 Assistant ID, PDF 파일, 프롬프트를 Playground에서 테스트했습니다. 놀랍게도 여기서는 **정상적으로 결과가 생성**되었습니다. 문제는 Assistant 자체가 아닌, Edge Function 코드 어딘가에 있다는 확신을 얻었습니다.

* **프롬프트 단순화:** 복잡한 큐카드 생성 요구 대신 "파일 내용을 요약해줘" 와 같이 아주 간단한 프롬프트를 사용해 보았지만, 결과는 마찬가지로 빈 응답이었습니다.

* **Vector Store 파일 상태 확인:** 파일 추가 후 `retrieve` API를 호출하여 파일 상태가 `completed`인지 확인하는 로직을 추가했습니다. 파일은 정상적으로 처리되고 있었습니다.

* **결론:** 문제는 Assistant나 Vector Store 자체가 아니라, **Edge Function 내에서 OpenAI로부터 받은 스트리밍 응답을 제대로 파싱하거나 클라이언트로 전달하지 못하고 있다**는 쪽으로 무게가 실렸습니다. 즉, 스트림 연결은 되었으나 내용물이 비어있는 파이프와 같은 상황이었습니다.

  

### 3단계: 스트리밍 데이터 파싱의 미로 - 데이터 구조가 왜 이래?

텅 빈 응답의 원인이 Edge Function 내 스트림 처리 로직에 있을 것이라 판단하고, 코드 내부 로깅을 강화하며 문제 추적에 나섰습니다. 드디어 로그를 통해 OpenAI로부터 데이터 조각들이 수신되는 것을 확인했지만, 여전히 클라이언트에는 데이터가 오지 않았습니다. 로그를 자세히 분석한 결과, 스트리밍 **데이터를 파싱하는 로직**에 결정적인 오류들이 있음을 발견했습니다.
![[image copy 2.png]]
  클라이언트 응답은 비어있었지만 Edge Function의 로그를 보니 확실히 Assistant API로부터 스트리밍 데이터를 받아오는 것을 확인할 수 있었습니다.

**문제 1: 이벤트 타입 필드 착각 (`event` vs `object`)**

* **증상:** OpenAI Assistants API v1 스트리밍 응답에서는 이벤트 타입을 `event` 필드로 구분했습니다 (`event: thread.message.delta`). 그래서 당연히 v2에서도 그럴 것이라 예상하고 `if (eventData.event === 'thread.message.delta')` 와 같이 코드를 작성했습니다.

* **실제:** 하지만 v2 응답을 로깅해보니, 이벤트 타입은 `event` 필드가 아닌 **`object` 필드**에 담겨 있었습니다 (`object: 'thread.message.delta'`). 이 때문에 조건문이 항상 `false`가 되어 델타(텍스트 조각) 처리 로직이 전혀 실행되지 않았던 것입니다!

* **해결:** 조건문을 `if (eventData.object === 'thread.message.delta')` 로 수정했습니다.

  

**문제 2: 델타 데이터 접근 경로 오류 (`data.delta` vs `delta`)**

* **증상:** 이벤트 타입(`object`)은 올바르게 감지하도록 수정했지만, 정작 중요한 텍스트 조각(`value`)이 담긴 `delta` 객체가 여전히 `undefined`로 나왔습니다.

* **원인:** 이전 경험이나 다른 API 구조를 바탕으로 `delta` 객체가 `eventData.data.delta` 경로에 있을 것이라 잘못 추측했습니다. 즉, 이벤트 데이터 객체 안에 `data`라는 키가 있고, 그 아래 `delta`가 있을 것이라고 예상한 것이죠.

* **실제:** 로그를 통해 확인한 실제 `delta` 객체의 경로는 **`eventData.delta`** 였습니다. 즉, `data` 객체 없이 `eventData` 바로 아래에 `delta` 키가 위치했던 것입니다.

* **해결:** `const delta = eventData.data?.delta;` 코드를 `const delta = eventData.delta;` 로 수정했습니다.


  

**(부가 문제) TypeScript 스코프의 덫:** 위 파싱 오류를 수정하는 과정에서 `try...catch...finally` 블록 내 변수 스코프 문제로 인해 `catch`나 `finally`에서 리소스 정리용 변수(`OPENAI_API_KEY`)에 접근하지 못하는 TypeScript 오류를 만나기도 했습니다. 이는 변수 선언 위치를 `try` 블록 밖으로 옮기거나, 정리 함수를 내부 함수로 만들어 클로저를 활용하여 해결했습니다.

  

**배운 점:**

* **공식 문서는 시작일 뿐, 실제 응답을 믿어라:** API 문서는 훌륭한 가이드라인이지만, 특히 베타 버전이거나 복잡한 API의 경우 실제 응답 데이터 구조는 다를 수 있습니다. `console.log`를 통해 **실제 수신되는 데이터 구조를 직접 확인**하는 것이 무엇보다 중요합니다. 로그가 진실을 말해줍니다.

* **상세한 로깅의 힘:** 각 단계별로 변수 값과 객체 구조를 자세히 로깅한 덕분에 문제를 정확히 진단하고 해결할 수 있었습니다. "데이터가 안 와요"에서 "아, `object` 필드를 봐야 하는구나!", "어, `delta`가 바로 아래에 있네?"로 나아갈 수 있었던 것은 모두 로그 덕분입니다.

* **Optional Chaining (`?.`)의 함정:** `?.`는 코드를 간결하게 하지만, 객체 경로를 잘못 추측했을 경우 오류 없이 조용히 `undefined`를 반환하여 문제를 숨길 수 있습니다. 데이터 구조가 확실하지 않다면, 로깅을 통해 검증하거나 명시적으로 경로를 확인하는 것이 더 안전할 수 있습니다.


## 결론: 삽질 끝에 얻은 교훈

  

길고 험난한 과정을 거쳐 마침내 Supabase Edge Function과 OpenAI Assistants API v2를 이용한 실시간 큐카드 스트리밍 기능을 성공적으로 구현했습니다! 🎉 포기하고 싶었던 순간도 있었지만, 문제를 하나씩 해결해나가면서 얻은 성취감은 매우 컸습니다.

비록 많은 시간과 노력이 들었지만, 이 과정을 통해 스트리밍 기술, OpenAI API, 그리고 디버깅 능력에 대한 이해도를 크게 높일 수 있었습니다. 이 글이 비슷한 문제로 어려움을 겪는 다른 개발자분들께 시행착오를 줄이는 데 조금이나마 도움이 되기를 바랍니다.
